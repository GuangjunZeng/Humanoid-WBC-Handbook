# Repository instructions for paper-library work

When the user explicitly asks to update the paper library or one paper topic, follow `docs/on-demand-paper-update.md` end to end. The update is user-triggered and bounded: do not create a schedule, subscription, push, Feishu/email/message workflow, or unattended background job.

For deep paper briefs, reuse only the single-paper analysis method described in `docs/paper-interpretation.md`. Do not invoke or reproduce Scholar Inbox, daily-digest, recommendation-push, or delivery features from `paper-daily`.

Treat `content/papers/catalog.json` as the canonical coverage inventory and `content/papers/registry.json` as the quality-gated deep-read set. A discovered paper enters as `queued`; promote it to `deep_read` only after the full PDF, official-code status, key figures, Chinese-first brief, safety boundary, and all repository checks pass.

Use primary records for paper identity and official-code status. Do not substitute a third-party reimplementation for author code. Keep classic-field anchors, papers with verified official code, hardware/negative evidence, and topic-role gaps visible in the update report.

For cross-run deduplication, query-yield rotation, evidence-linked topic evolution, and GitHub Issues backfill, also read `docs/social-discovery-evolution.md`. Preserve every root post/Issue and exact reply/comment URL, keep raw high-volume results under ignored `var/`, and do not treat search volume as reviewed evidence.

When the user explicitly asks to collect or update social-platform engineering experience, read `docs/social-browser-automation.md` and `docs/social-collection.md` before acting. The default no-API-fee path for X and Xiaohongshu is a signed-in visible browser; Zhihu may use its official API for discovery and a signed-in visible browser for bounded enrichment. The browser workflow is user-triggered, not scheduled. Do not ask the user to open posts one by one: automate search, navigation, bounded body/reply extraction, image screenshot review, canonicalization, deduplication, and candidate generation. Pause only for initial/expired login, CAPTCHA, risk control, paywall, or unavailable content. Never inspect or persist cookies, browser profiles, credentials, SMS codes, hidden APIs, transient access tokens, or private content, and never auto-publish a community candidate as reviewed guidance. Every browser result must retain its original post/reply URL and `collection_completeness.status=partial_visible`; never describe a bounded visible run as all posts or all replies.

The official X API is an optional paid mode, not the default. Read `docs/x-api-automation.md` only when the user explicitly selects that mode. In API mode, keep the Bearer Token in an environment variable, consume complete API pages, persist an unfinished `next_token`, and advance `since_id` only after that result window is fully drained. In free browser mode, use only visible DOM/UI controls, never hidden network endpoints, and stop for login or platform controls.
