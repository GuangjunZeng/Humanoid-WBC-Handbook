# 开源项目独立解读规范

这套规范服务于没有论文、论文尚未深读，或仓库能力明显超出论文快照的高质量 WBC 开源项目。项目页与论文页是两条证据链：项目页回答“这份代码现在实际提供什么”，论文页回答“论文在固定实验中支持什么结论”，两者不得互相代替。

## 收录门槛

- 默认只考虑用户触发更新时官方 GitHub 记录不少于 80 stars 的仓库；60–79 stars 只有在官方归属、topic 缺口和论文证据同时成立时才可书面例外，低于 60 不收。
- stars 只用于发现，不是可信度、技术正确性或真机安全证明。
- 只放进既有七个 topic，不新增 topic。一个项目可以属于多个 topic，但每个归类必须能由源码或一手文档支持。
- 聚合仓库只用于发现候选。标题、描述、图片和结论必须回到官方仓库、固定 commit、论文或官方文档核验，不复制聚合仓库的解读文字。

## 独立页要求

每个 `deep_review` 项目必须有完整中英文页。中文页以中文为主，关键术语采用中英文结合；英文页完整表达同一证据边界。两页都必须包含：为什么收录、工程问题、架构与数据流、至少两个固定 commit 的代码定位、最小复现路径、能力边界、工程判断与硬件安全边界，以及一手来源。

项目审阅固定到 40 位 commit。仓库后续更新不会自动改写结论；只有用户要求更新时，才重新抓取官方元数据、比较 commit、复核源码并更新星标快照。项目已有论文时，目录关系必须改成 `official_paper_code`，但项目独立页仍可保留，用于解释当前仓库工程结构。

## 状态与自动检查

`queued` 只代表通过发现门槛，不能拥有冒充完整解读的页面。`deep_review` 需要双语页面、commit、代码链接和安全边界全部通过检查。CI 对中文深度、英文完整性、固定 commit 链接、语言互链和章节结构做最低门禁；人工审阅仍负责判断代码定位是否真正支持文字结论。
